# IoT bridge recovery

Command flow is `PENDING (cloud) → LEASED (cloud, still PENDING) → CLAIMED (SQLite) → CONFIRMED/ACCEPTED (cloud) → PUBLISHING → PUBLISHED → TERMINAL`. Leasing is atomic and gateway-scoped, expires after at most 15 seconds and never outlives the command. The bridge durably records the command and lease identity before confirmation; it publishes only after confirmation. A restart resumes a durable `CLAIMED` record and confirmation is idempotent for the already-accepted gateway command. QoS 1 PUBACK advances only to `PUBLISHED`; only a controller acknowledgement can establish execution.

If publication throws or restart occurs during `PUBLISHING`, the record becomes `UNCERTAIN` and is never automatically republished. Gate and siren commands require authoritative physical reconciliation or expiry. A crash before SQLite persistence leaves the command `PENDING`; its lease expires and it can be safely leased again. A crash after persistence resumes the same durable identity. A crash after cloud acceptance resumes only the locally persisted record, closing the previous claim-before-persistence loss window.

Inbound QoS 1 device events use MQTT 5 custom acknowledgement handling: they are validated and inserted by original ID before PUBACK is returned. Storage or capacity failure withholds success so the broker can redeliver. Duplicates are ignored. Batches are deleted only when the cloud returns accepted IDs; failures receive bounded backoff. SQLite at `/data/bridge.sqlite` uses WAL, foreign keys, full synchronous writes and a busy timeout. Heartbeats are not durably queued; any buffered heartbeat older than the 35-second freshness threshold is acknowledged and discarded rather than forwarded with a new server receipt time.

Security checkpoints retain the highest delivered version per controller/scope. Sync/reconnect publishes only current, unexpired, higher versions as non-retained messages. Historical modes are not replayed.
